# ADR-0053: Program holds what it shows until what replaces it is ready

Accepted · 2026-10-28 · Amended 2026-11-13 ([#1168](https://github.com/KeeprDigital/stream-keepr/issues/1168)): application fonts settle before ready, and hold readiness only, never a display · Amended 2026-11-14 ([#1201](https://github.com/KeeprDigital/stream-keepr/issues/1201)): a Deck List waits only for the art its shown boards draw · Amended 2026-11-15 ([#1201](https://github.com/KeeprDigital/stream-keepr/issues/1201)): a Deck List draws each board's art from the smallest Scryfall image its cards need

### Decision

**A Screen Mode rendering is ready once what it shows has settled**: its display has declared its data settled, its fonts have loaded or failed, and every image, video and pending part inside it has loaded or failed. This is Rendering Readiness, owned by `app/modules/screen-mode/readiness.ts` and the Screen renderer's frame (`Screen/RendererFrame.vue`).

**The renderer double-buffers modes.** On a mode change the incoming mode renders hidden behind the one on program, and the renderer cuts to it once it is ready. On a first load nothing shows until then. A mode left before it was ready is dropped; going back to the mode on program drops the one loading. Only the rendering on program hosts overlays. A rendering not ready after `SCREEN_MODE_READY_TIMEOUT_MS` (10 s) is shown anyway with a console warning, so a hung read or image never pins program to the outgoing mode.

**Every display declares.** `ScreenModeBase` takes a required `ready` prop, so a mode built on it cannot forget; a display without it calls `useScreenModeReady` (Background, Feature Match Overlay, Broadcast Graphics). Its data composable answers `ready`: its first read answered or failed (Screen Mode Data Freshness's `answered`), and whatever it stages loaded. Nothing declared is not ready, because a display is an async component that declares only once its chunk has loaded. A part that loads on its own declares too (the Card Spotlight's card), or marks itself `data-render-pending` while it loads (a Background Layer stack resolving library media, an Animation Effect loading its module); the frame waits for both, then for every `<img>` and `<video>` inside it.

**Fonts settle before ready, library and application alike (#1168).** Each font host waits for both kinds of font it paints: the Screen renderer's frame for its Theme's `heading` and `body` and its mode's typography Mode Tokens, and each graphics host (Broadcast Graphics, Feature Match Overlay) for its Graphic Items' typography and Graphic Placeholder Styles. A library font loads as a `FontFace` (ADR-0050). An application font arrives through the bundle's `@font-face` with `font-display: swap`, so the host asks `document.fonts.load` for each face it paints, by family, weight and style (`useApplicationFontFaces`). A rendering is not ready until both kinds have settled, every requested face loaded or failed, bounded by the frame's existing timeout and no other; `data-font-ready` and `data-font-error` report that combined state (`useCombinedFontFaces`), as does the Feature Match Overlay's `data-export-ready`. Application fonts hold Rendering Readiness and nothing else: a host's display hides while its library fonts load, and never for an application font. A face a display already on program comes to need swaps in when it arrives rather than taking the display off air, and a rendering whose application face never settles goes on program at the timeout, in the fallback face. An application face that fails, or that its stylesheet does not declare, shows the fallback face, as a failed library font does.

**What the wait covers is the token's face, in the Latin subset.** It waits for the face each Theme typography token and each Graphic Item typography or Graphic Placeholder Style names: its family, its weight and its style. `document.fonts.load` with its default text selects the faces whose `unicode-range` covers a space, which is the Latin subset only. It does not wait for a weight or style a display's own stylesheet asks for beyond the token's (Player History's `.opponent { font-weight: bolder }`, the Pairings winner, the Deck display's `font-medium`, `font-semibold` and `font-bold`), nor for any other subset, Latin Extended included, so a name with ł, ő, ž or ğ paints those letters from a face that is not loaded yet. Those faces swap in when first painted.

**Inside a mode, a change that brings new images is staged.** `useStagedScreenContent` holds what a rendering shows until the images of what replaces it have preloaded and decoded (`preloadImages`), a newer change superseding one still loading, a failed image counting as loaded so its fallback shows. Most Played Cards stages each page with its page indicator, Archetype Spotlight its whole read. The Deck List keeps its own staged swap, now on the shared preload, and waits only for the art its shown boards draw: a board shown as a list, or hidden by its board selection, has its art warmed once that has loaded, so a later switch to its grid finds it loaded (#1201, `deckBoardsShowingArt`). Each board draws, and so preloads, the smallest Scryfall image no narrower than the widest card its board could solve to on the whole Event Canvas, in output pixels (the output's fit scale times its device pixel ratio): `small` (146 px) or `normal` (488 px), `deckArtSizes`. A hundred-card grid on a 1080p output solves to ~100 px and draws `small`, a tenth of the bytes; a constructed deck, a Seat's Commanders, a companion and a stacked strip draw `normal`. A change to the layout or the output that needs larger art loads it in place of the image shown, without a staged swap. The Card Spotlight keeps its card on program until the replacement's images have loaded, then plays its exit and entry.

### Why

Some modes held program and others did not. The Deck List preloaded its card art and swapped whole; Most Played Cards mounted its grid at once and painted card by card on every page; every mode change showed the incoming mode's empty scaffold ("TBD vs TBD", an empty table) while its first read was in flight. Doing it once in the renderer covers every mode, present and future, without each re-implementing a preload.

### Consequences

- A mode change shows nothing new until the incoming mode is ready, up to the timeout. A read that fails settles as ready, showing what the mode shows on error.
- Two renderings are briefly live during a mode change, each reading its own data and holding its own Realtime Subscriptions.
- A Broadcast Graphics output whose Live Session read fails reaches program only at the timeout.
- A video whose source changes, a video Background Layer's or the Feature Match Overlay Frame's, keeps playing until the new source has its first frame or fails (`ScreenMediaBackground`).
- A Take cannot be held on one output, whose animation phases follow the shared clock with every other. Instead a Broadcast Graphics output loads every image its stack can put on air once its content URLs resolve, and holds the loaded images while the stack names them (`createImageRetainer`): its library content is `no-store`, so only an image still held is reused. Videos are not preloaded.
- A Broadcast Graphics canvas whose library font fails now shows in the fallback face, as the Feature Match Overlay does, rather than staying hidden: a blank graphic is worse on air than the wrong face.
- Not covered: a Screen Output navigated to another Screen still blanks while it loads, because the display session unmounts the renderer. Nothing in the app moves an output between Screens, and holding one would need each rendering to keep its own Screen, Event, Theme and capability.
- `test/nuxt/components/Screen/Renderer.test.ts` pins the hold, `test/nuxt/modules/screenModeReadiness.test.ts` the declarations and staging.

### Rejected alternatives

- **Each mode preloading its own media, as the Deck List did.** It covers only the modes that remember to, and none of them covers the mode change itself.
- **Hold program by scanning the DOM alone, with no declaration.** An async display's chunk has not mounted when the scan runs, so an empty rendering would look ready.
- **Vue `<Suspense>`.** Still experimental, and suspending setup would keep the incoming rendering from mounting, which is what starts its media loading.
- **An application font also hiding its display until it first settles, or until its rendering is on program (#1168).** Every display mounts inside the Screen renderer's frame, which hides the whole rendering until it is ready and puts it on program then, so a display-level rule would decide nothing a viewer sees; it served only a standalone mount no page has.
- **Waiting on `document.fonts.ready` after render (#1168): left for a later decision, not rejected.** Once a rendering has painted, `document.fonts.ready` settles when every face its text actually uses has loaded, display-stylesheet weights and every subset included, so waiting on it under the same timeout would cover every painted face. #1168 waits for the token faces only.
